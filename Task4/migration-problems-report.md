# Анализ узких мест при миграции на микросервисную архитектуру

## 1. Ключевые процессы и компоненты миграции

|Категория|Компоненты / Процессы|Риски при миграции|
|-|-|-|
|Данные|• Файловые архивы Excel/PDF на общем диске</br>• Две 1С-базы в файловом режиме</br>• Отсутствие единой модели данных|• Несовместимость схем при декомпозиции монолита</br>• Дублирование данных между сервисами (например, ФИО пациента в 5+ местах)</br>• Потеря целостности при распределённых транзакциях|
|Инфраструктура|• Единый физический сервер Windows Server 2022</br>• Локальное размещение в офисе|• Отсутствие отказоустойчивости для микросервисов (требуется кластер)</br>• Недостаточная сеть для межсервисного трафика (100+ вызовов на 1 бизнес-операцию)</br>• Отсутствие среды для канареечных релизов|
|Интеграции|• OLE между 1С-системами</br>• TCP/IP к ККМ</br>• Ручной обмен с лабораторией|• Отсутствие стандартных протоколов (REST/gRPC)</br>• Синхронные вызовы → каскадные отказы при высокой нагрузке</br>• Нет механизмов компенсации при сбоях (Saga pattern)|
|Безопасность|• Только доменная аутентификация</br>• Нет аудита доступа к файлам|• Усложнение контроля доступа в распределённой системе (требуется единый шлюз авторизации)</br>• Риск утечки ПДн при неправильной маршрутизации между сервисами|
|Персонал|• 3 IT-специалиста</br>• 40 бизнес-пользователей|• IT-команда обладает техническими навыками, но требует архитектурной дисциплины (декомпозиция домена, распределённые транзакции).</br>• Сопротивление изменениям при переходе от «одного файла» к «множеству сервисов»|

## 2. Классификация проблем по категориям

|Категория|Проблема|Влияние на производительность|Вероятность|
|-|-|-|-|
|Инфраструктура|Единый сервер → узкое место при параллельных вызовах 10+ микросервисов|Критическое: задержки >5 с при 50+ одновременных пользователях|Высокая|
|Инфраструктура|Сеть 1 Гбит/с → недостаточно для межсервисного трафика (100+ вызовов/операция)|Среднее: рост задержек на 30–50% при пиковой нагрузке|Средняя|
|П/о|Синхронные вызовы → каскадные отказы при сбое одного сервиса|Критическое: полная недоступность системы при отказе сервиса записи|Высокая|
|П/о|Дублирование ПДн → несогласованность данных между сервисами|Высокое: ошибки при формировании отчётов, конфликты при обновлении|Высокая|
|Интеграции|Протокол OLE → невозможность горизонтального масштабирования 1С|Критическое: блокировка при одновременной работе >5 пользователей|Высокая|
|Данные|Отсутствие классификации → шифрование всех данных «единым ключом»|Среднее: снижение скорости обработки на 40% из-за избыточного шифрования|Высокая|
|Персонал|Нет специалиста по данным. Администратор сети способен только развернуть кластер Kubernetes|Среднее: общая низкая производительность системы из-за неопимальных (коробчных) настроек.|Средняя|
|Процессы|Ручное тестирование → пропуск регрессий в интеграциях|Среднее: откаты после релиза, потеря доверия пользователей|Высокая|

## 3. Рекомендации с приоритизацией

|Приоритет|Мера|Обоснование|Срок реализаци|
|-|-|-|-|
|Критический|Внедрение асинхронной коммуникации (очереди: RabbitMQ/Kafka) для критичных операций (запись пациента → уведомление)|Устраняет каскадные отказы, снижает задержки на 70%|1 месяц|
|Критический|Создание единой модели данных с мастер-данными пациентов (единый сервис справочников)|Устраняет дублирование ПДн, гарантирует согласованность|1-2 месяца|
|Высокий|Миграция с файлового режима 1С на клиент-серверный режим + выделенный сервер|Устраняет блокировки при параллельной работе|1 месяц|
|Высокий|Внедрение классификатора данных при приеме (теги: pii, medical_secret)|Позволяет применять шифрование только к чувствительным данным → +40% производительности|2 месяца|
|Средний|Развертывание кластера Kubernetes на 3+ нодах с балансировщиком|Обеспечивает отказоустойчивость и горизонтальное масштабирование|2-3 месяца|
|Низкий|Автоматизация тестирования интеграций (Postman + Newman в CI/CD)|Снижает количество регрессий после релизов|3 месяца|

## 4. Проблемы и решения

|Проблема|Последствия для системы|Решение|Метрика успеха|
|-|-|-|-|
|Синхронные вызовы между сервисами|При сбое сервиса уведомлений — невозможность завершить запись пациента|• Асинхронная отправка уведомлений через очередь</br>• Паттерн «Компенсирующая транзакция» для отмены записи|• Отказ одного сервиса не блокирует бизнес-операцию</br>• Время обработки записи < 2 с при 99-м перцентиле|
|Дублирование ПДн в 5+ сервисах|Расхождение ФИО пациента в карте и журнале приёма|• Единый сервис справочников (Master Data Management)</br>• CQRS: запись только в мастер, чтение — с реплик|• Согласованность данных в реальном времени (лаг < 100 мс)</br>• Отсутствие конфликтов при обновлении|
|Файловый режим 1С|Блокировка базы при >5 одновременных пользователях|• Миграция на клиент-серверный режим 1С</br>• Выделенный сервер БД (MS SQL/PostgreSQL)|• Поддержка 50+ одновременных пользователей без блокировок</br>• Время отклика 1С < 500 мс|
|Отсутствие классификации ПДн|Шифрование всех данных → падение производительности на 40%|• Автоматическая классификация при инжесте (регулярные выражения + ML)</br>• Шифрование только тегированных полей|• Производительность обработки ПДн на уровне нечувствительных данных (+35%)</br>• Соответствие ФЗ-152 без избыточных затрат|
|Единый сервер для всех сервисов|Полный простой системы при сбое сервера|• Кластеризация: минимум 3 ноды + балансировщик</br>• Георезервирование в другом дата-центре РФ|• Доступность 99.95% (простой ≤ 4.32 ч/год)</br>• Восстановление после сбоя < 5 мин|

## Ключевые выводы

1. Главное узкое место — архитектурное: синхронные вызовы и отсутствие единой модели данных создадут системные сбои уже на этапе MVP.
2. Критический путь миграции:
    * Месяц 1: асинхронные очереди + клиент-серверный режим 1С
    * Месяц 2: единый сервис справочников + классификатор ПДн
    * Месяц 3: кластеризация + автоматизация тестирования
3. Риски снижения производительности:
    * Без асинхронизации: задержки вырастут в 3–5× при 5× росте пользователей
    * Без классификации ПДн: шифрование «всего подряд» снизит пропускную способность на 40%
    * Без кластеризации: простои при сбое сервера будут 100% (вместо целевых 0.05%)
4. Соответствие требованиям РФ: все решения учитывают необходимость хранения ПДн на территории РФ и использования сертифицированных СКЗИ.
